PRODUCT TARGET

Build one useful workflow:

A finance operator imports a messy set of customer invoices, credit memos, and supporting documents. The system produces auditable per-customer net invoiced totals, explains which documents count and why, identifies contradictions and unresolved cases, requests human decisions where necessary, and resumes correctly after those decisions.

Use Invoice Sandbox as the initial external benchmark because an adapter already exists. Confirm its exact task, permitted inputs, and scoring semantics before implementation.

Keep accounting terminology precise:
- Net invoiced totals are not necessarily outstanding balances.
- An invoice is not evidence that cash moved.
- A benchmark score is not proof of payment execution or production readiness.

Support one company and USD for this MVP. Keep unrelated payroll, treasury, forecasting, and live banking work outside the critical path.

The product should demonstrate useful behavior when documents arrive late, contradict one another, or introduce an unfamiliar layout. It should do more than replay a fixed sequence.

WORKER A — CASE STATE AND ACCOUNTING BACKEND

Goal: implement a durable, permissioned case lifecycle that preserves accounting correctness and supports human resolution.

Required behavior:
- Preserve source documents and versions.
- Give every document a recorded outcome or unresolved state.
- Use explicit statuses with validated transitions.
- Separate proposed conclusions from accepted accounting changes.
- Bind human decisions to an immutable proposal and its evidence version.
- Reject stale or conflicting decisions.
- Make replayed decisions and retries idempotent.
- Prevent duplicate accounting effects.
- Preserve unresolved cases across restarts.
- Keep missing evidence visible.
- Enforce access rules in the backend.
- Keep totals and accounting arithmetic deterministic.

Use Convex where it already serves these needs. Avoid infrastructure migration without a demonstrated blocker.

Acceptance requires focused tests for duplicate ingestion, revisions, stale approvals, conflicting answers, replay, restart recovery, and unauthorized actions.

WORKER B — INVESTIGATION AND REVIEW

Goal: implement a bounded agent workflow that can investigate a case using evidence and tools.

The investigator must be able to:
- Inspect source documents.
- Retrieve related invoices, credits, customer records, and relevant policy.
- Compare conflicting evidence.
- Choose an appropriate next tool call.
- Propose a disposition with supporting references.
- Identify missing information.
- Ask a specific human question when evidence is insufficient.
- Resume using the recorded response.

Use a bounded observe → tool action → result → next action loop where judgment is needed. Keep calculations and accounting invariants in ordinary code.

Use at most two AI roles:
1. Investigator.
2. Independent reviewer, if it provides measurable value.

If implementing the reviewer:
- Give it access to original evidence.
- Require it to identify unsupported claims or contradictions.
- Allow approve, reject, and request-more-evidence outcomes.
- Do not implement it as an automatic agreement with the investigator.
- Distinguish model review from deterministic validation.

Preserve useful parser learning, but test generated parsers against multiple examples and regressions. Do not treat one model extraction as independently verified truth.

Record concise decision summaries, source references, tool calls, usage, and outcomes. Do not request or expose hidden chain-of-thought.

Treat document content as untrusted data. Documents must not grant permissions, alter system instructions, or authorize external actions.

Label the implementation honestly. A rules-based worker should be described as such.
