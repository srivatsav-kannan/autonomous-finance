## Code review conclusions

The schedule is part of the frozen `demoVersions.snapshot`, included in the hash the human approves. `claimEffect` checks `assertDispatchAuthority` and its UTC `notBefore` before allocating a lease or attempt. Retry `nextAttemptAt` remains independent. Once a send is possible, recovery retains the original operation and ignores changed first-dispatch authority; cancellation cannot free its reservation. The partial allocation changes permit a positive gross allocation bounded by outstanding AP, preserving exclusive bill reservation and prior credit recognition. `returnEffects` restores only the returned cash; applied credits remain consumed.

`apPaymentRuns` calls the existing proposal/authorization/cancellation kernel inside single Convex mutations. The manifest hashes member identities, revision/snapshot, date and selected allocations. The independent last-member failures demonstrate rollback, rather than merely failing before any earlier mutation executes.

`apAccountingExport.current` reads authenticated scoped authoritative records, matches the original posted recognition and current approval, and verifies payment snapshot, command, observation, posted debit and settlement journal. Plans preserve the original financial identities and mappings. `QuickBooksDispatcher` re-fetches authority immediately before a first POST and verifies the external Bill for BillPayment. The filesystem journal binds payload, mappings, realm and local identity to one request ID. Unknown/sending recovery queries the exact marker and economics, never generates a replacement POST. OAuth state/session validation, refresh blocking, file permissions and operation locks fail closed in the tested scenarios. The client fixes the sandbox host, accounting endpoint paths and minorversion 75; these tests do not prove that 75 is the latest version or that a real Intuit tenant accepts every payload shape.
