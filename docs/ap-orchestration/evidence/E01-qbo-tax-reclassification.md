# E01 QBO tax reclassification and historical receipt recovery

Source baseline: `3ee360d` (includes B `8598cc7` and `a5aaa71`). Type checkpoint: `d33c7ddbac22d1951a176909834d94fd641a7b71`. Frozen issue spec remains `b795ea7028c3e8eb91446dae5623e5e2183bcabb32447a54deefd9db238de565`.

This component consumes the existing authenticated `apClose:accountingExport` result. It does not select recovery eligibility, a rate or jurisdiction; change active policy or mappings; initiate banking; modify the original Bill; or call a live provider. All protocol results below use an injected transport double and synthetic policy/evidence.

## Separate approved accounting operation

`tax_reclassification` requires a close action whose approval ID is the action ID, exact `ap_tax_adjustment` source bound to the original recognition journal, original case/Bill/supplier, and an already synchronized original Bill with the same scope, vendor, USD currency and valid immutable payload hash. Its saved original is read-verified immediately before a new external write. Current backend approval/seat/policy authority is loaded again before that write, with the same authenticated submitter and plan hash.

Every exported movement retains its ordered debit/credit pair, amount, supplier, store/Class and department/Location. Only known local expense or noncash-asset accounts are supported. Each needs explicit operator mapping to an allowed corresponding QBO account type, including any tax receivable account; missing or mismatched mappings hold. AP, cash, accrued liability, changed coordinates and same-account treatment-only movements do not pass this adapter. The existing project JournalEntry Entity/billability combination remains held; a Customer entity is not substituted for the approved Vendor.

New tax operation plans freeze approval/journal hashes, the aggregate original authority hash and the submitting subject alongside existing request identity, mapping hash and exact payload. This is additive for the new kind; existing Bill/accrual/cost operation bytes are not migrated. New plans still require the original operation's mapping fingerprint to match the reviewed current configuration; incompatible mapping changes require explicit resolution and are not automatically remapped.

## Explicit read-only historical recovery

`apAccountingReceiptAccess:tax` requires a currently active independently authenticated human and exact organization/run/provider/environment/account scope. It checks the retained approved action hash and posted journal hash/source. It grants access only to a receipt; it does not restore current-policy write authority. For a scoped non-tax action it returns null so existing close verification remains unchanged.

`recoverCloseReceipt` permits only an existing sending/unknown/succeeded tax operation. It checks the saved plan hash, original request ID, mapping hash, original submitting subject, approval/journal bindings and recorded submission authorization. It rechecks current reader identity and scoped access before a provider read. It calls only `find` or `verify`: no `execute`, `create`, update, new operation, new request ID or remapping. A found exact result records the external ID/SyncToken on the original operation. Empty, malformed or conflicting responses never authorize another POST. An empty valid result stays unknown with `unknown_not_found_no_repost`; the UI receives a hold without a verified timestamp. A later reader is not substituted for the original authorizer.

The request-owned bridge uses this path for explicit tax verify. Provider-free status can show saved tax receipts after current policy retires: `authority=historical_receipt_only`, `externalWritesAllowed=false`, an authority hold, and `externalReadsAllowed` only for the authenticated Increase sandbox scope. New preview and submit retain their original current-authority gates. Status does not request or refresh an OAuth token. D owns the matching selector/receipt recovery controls.

## Primary API reference

The current [JournalEntry page](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/journalentry) and [Account page](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/account) were queried again; their static response was only the loading shell. Intuit's published [JournalEntryLineDetail schema](https://static.developer.intuit.com/sdkdocs/qbv3doc/ipp-v3-java-devkit-javadoc/com/intuit/ipp/data/JournalEntryLineDetail.html) specifies PostingType, Entity, AccountRef, ClassRef and DepartmentRef. Its [AccountTypeEnum](https://static.developer.intuit.com/sdkdocs/qbv3doc/ipp-v3-java-devkit-javadoc/com/intuit/ipp/data/AccountTypeEnum.html) distinguishes noncash asset and expense categories from Bank, Accounts Payable and liability categories. These official schema references corroborate the narrow accounting payload, not current tenant acceptance or tax eligibility. No QBO tax code, tax filing/refund endpoint or merchant-processing action is invoked.
