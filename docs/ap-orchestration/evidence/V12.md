## Adversarial coverage

- A return JE that has only been created does not release the restoration gate. Separate successful readback is required. Missing AP location, changed bank location, unexpected header location or an added processing flag each retain the hold. Exact restoration plus harmless provider metadata permits release.
- Changing a saved zero-cash application's linked JE retains its application-verification hold. Restoring the exact linked row releases it, without creating another operation.
- An accepted response lost after the first POST becomes `unknown`. Empty searches preserve the same request ID, bytes, attempt count and first submission authorizer. A later exact search recovers it, still with one POST. A newer caller cannot replace the original authorizer.
- Missing or changed settlement header location, extra line location, extra class, changed linked Bill, and `ProcessBillPayment:true` each reject ambiguous recovery and do not repost or replace the original authorization.
- A changed external original Bill department is detected before linked settlement submission; its operation has zero attempts and no submission authorizer. A changed local settlement journal hash, extra project dimension, or command binding prevents authoritative export.
- Mutating recognition approval identity, original policy authority, credit coverage or credit supplier rejects plan construction. These are additional defense-in-depth mapper probes; authenticated exports remain the trusted input boundary.
- Explicit null settlement authority and legacy absence each preserve the exact independently written accounting-only payload bytes, with no inferred header/line dimension. Legacy absence and explicit null remain distinct in local authority.
- A generated dimension-bearing plan altered to request merchant processing is refused before any POST. A saved successful payment that gains the processing flag fails readback. The existing accounting-only suite separately checks the direct client boundary before token lookup.
