## Actionable findings

### V4-F1 — high: parser line renumbering mints capacity from the same originals

Affected baseline: `convex/lib/apSystem/businessLedger.ts:34`, `:53`, and legacy comparison at `:113`. Current grouping uses source SHA256 **plus parser line ID**, and prior consumption lookup still requires equality of line ID. The earlier source-hash amendment protects renamed source IDs only while the line ID remains unchanged.

Independent invoice reproduction in `v4-business.test.ts`:

1. Recognize one of two original 3,850-cent units: one bill and one journal for 3,850.
2. Ingest a second invoice using the exact original PO and receipt bytes/hashes. Change only source identity/name/delivery metadata and the parser-assigned PO/receipt line IDs; update the candidate references to those IDs.
3. Review the second case, propose acceptance of both units, and obtain the configured owner and finance votes.
4. Baseline succeeds: **two bills, two journals, recognized total 11,550 cents**. The shared originals support **two units / 7,700 cents**, so one unit / 3,850 cents was counted twice. The independent test expects rejection and fails.

The second independent manifestation in `v4-credits.test.ts` recognizes a one-unit return credit for 4,235 cents against an 8,470-cent original. Another credit uses the exact same one-unit return original, with changed source and parser line IDs. Baseline accepts the second **proposal for 4,235 cents**. This probe stops at proposal and does not claim that the second credit was posted.

Required correction: bind capacity to stable original economic identity independent of parser line numbering, including return evidence and legacy recognition. Ambiguous same-original line identities must be held rather than creating more capacity. Preserve legitimate distinct original quantities and exact cumulative accounting. Both failing probes must pass unchanged after correction.

### V4-F2 — high: supplier bank change activates after retained verifier retirement

Affected baseline: `convex/apBusinessConfig.ts:344` through `:394`. `approveSupplier` checks the acting approver, exact proposal hash, status and subject-string separation, but does not revalidate the retained `verifiedBy` human and current verification-group authority before activation.

Independent reproduction in `v4-business.test.ts`: propose supplier revision 2 with a changed bank destination and the existing approved contact; an authorized verifier records a confirmed simulated callback; retire that verifier's human seat; a separate governor approves the exact proposal. Baseline returns `{ revision: 2 }` and activates it. The expected rejection fails.

Required correction: revalidate the retained verifier's configured active human identity and current verification-group membership at activation; require an independent underlying human seat from the approver. An old successful callback must not silently carry revoked authority into a new bank destination.

### V4-F3 — high: two subject aliases for one seat satisfy two-person quorum

Affected baseline: `convex/apBusiness.ts:343` through `:355` and retained-vote checks in `convex/lib/apSystem/businessAuthority.ts`. The comparisons distinguish subject/principal strings rather than the human seats they resolve to. `convex/demoPayments.ts:41` requires unique subjects but permits different subjects to bind the same active human seat.

Independent reproduction in `v4-business.test.ts`: use a valid owner stage with quorum 2 and no escalation group; configure `owner` and `second` subject bindings to the same `human-owner` seat, while both subject strings are members of the owner group. The fixture installs this configuration shape directly; static inspection confirms the public trusted configuration schema permits it. First subject vote returns pending; the second alias vote returns approved and recognizes the 3,850-cent obligation. The expected rejection fails.

Required correction: enforce distinct underlying active human seats for acting subjects and delegated principals across all counted positions, including retained vote revalidation. Merely rejecting one duplicate-subject form is insufficient when aliases or delegation refer to the same person.

All three findings were reported promptly to Master and the accounting implementation owner. Master triaged them for correction. Their acceptance status remains **open at this baseline**, even if fixes exist later in another branch.

## C2 code review and limits

The browser imports the official `@auth0/auth0-spa-js` SDK. Installed version 2.29.0 contains PKCE challenge/verifier, random state/nonce and callback transaction/state checks. The app uses memory caching, the fixed local callback, restricted case-ID app state and account selection. Convex 1.48.0's installed Auth0 adapter itself uses the ID token, consistent with the gateway's ID-token choice. `convex/auth.config.ts` supplies the configured issuer/application audience. `apIdentity:whoami` discovers identity without creating any seat or granting the first visitor ownership.

`createAPExternalAuthentication` creates a new Convex client for every request, sets only that request's token, queries verified identity, checks issuer/tokenIdentifier consistency, requires an explicit private subject allowlist, and checks scoped backend human access. Actual backend mutations enforce the configured active human again. Browser session generation checks occur after token acquisition, network return and parsed response; logout clears visible local access before waiting for network completion. Subject-scoped cookies cannot be reused across the two tested users.

The six new tests run an ephemeral loopback HTTP server with actual gateway/service/AP backend code and two explicitly synthetic identities, `auth0|alice` and `auth0|bob` under `https://v4-test.us.auth0.com/`. A test adapter supplies the identity normally produced by verified JWT processing. **It does not validate JWT cryptography or perform real Auth0 login, redirect, tenant settings, JWKS rotation or browser logout.** The older Auth0 HTTP/UI/config regression tests were inspected and rerun, but their doubles do not remove that limitation. No public response claim is made for untested provider payloads or live account grants.
